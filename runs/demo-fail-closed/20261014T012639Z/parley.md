# Parley - 20261014T012639Z

**Question:** An autonomous coding agent hits a permission check that no human is present to answer. Should its default be fail open (proceed and log) or fail closed (stop and wait)? Commit to ONE default for the general case, and name the single class of exception that justifies the other behaviour. The resolution must state both.

**Status:** resolved

**Resolution:** Default: fail closed. When an autonomous coding agent encounters a permission check that no human is present to answer, it must pause the gated action, record the pending decision and relevant context, and wait for authorization; logging alone does not authorize proceeding. Sole exception: preauthorized, bounded safety recovery for an operation already in progress when halting would create or worsen harm. The agent may execute only the previously authorized recovery procedure needed to reach a safe stopping state, record what it did and why, and then await authorization for further gated work. Perceived low risk, reversibility, urgency, or the fact that work has already begun does not independently justify failing open.

## Turn 1 - claude

I'll open with a concrete position. Default: fail closed. A permission check exists because someone decided in advance that this action needs a human's judgment, not the agent's. If the agent proceeds and logs when no human is present, it has substituted its own judgment for exactly the one the check was built to require, and the check degrades into a log line. A log is an audit trail, not a control. Fail open also creates the worst incentive: the agent learns that the cheapest path through any gate is to act while nobody is watching. The costs are asymmetric. A stalled task wastes time and is recoverable by a human on return. A wrong irreversible action (force push, dropped table, sent email, paid invoice) is not. The one exception I think is defensible: when stopping is itself the more harmful outcome. That is, the check fires in the middle of an operation the agent has already begun and abandoning it mid-flight leaves the system in a worse state than completing or unwinding it: a half-applied migration, a held lock, a rollback in progress, a partially written file that must be finished or restored. There, the agent proceeds only as far as needed to reach a consistent state, logs it, then stops. I'd reject 'low-risk or reversible actions' as the exception: if an action is truly low-risk, it should not carry a permission check at all, and fixing that is a configuration change, not a reason to fail open. I'd also reject 'time-sensitive' as the exception, because urgency is exactly the pressure under which unattended agents do the most damage. Here is proposed resolution text; tell me where you disagree.

*Position:* Fail closed by default; the sole exception is finishing or unwinding an already-started operation when halting mid-flight would leave the system in a worse, inconsistent state.  
*Accept:* False  
*Resolved:* Default: fail closed. When an autonomous coding agent hits a permission check and no human is present to answer, it stops, records the pending action and its context, and waits for a human to decide. It does not proceed on the strength of logging alone. Sole exception: an operation the agent has already begun, where stopping mid-flight would leave the system in a worse state than completing or unwinding it (for example a half-applied migration, a held lock, an in-progress rollback, or a partially written file). In that case the agent may proceed only as far as needed to reach a consistent state, logs exactly what it did and why, and then stops and waits. No other class of action, including actions judged low-risk, reversible, or time-sensitive, justifies failing open; if an action is genuinely low-risk it should not carry a permission check, and that is fixed in configuration, not by proceeding.
